# Connect the application to Supabase

The application uses Supabase directly for authentication, protected profiles, import history, workbook saving and deletion. Excel bytes are parsed in the browser. PostgreSQL independently checks the parsed JSON and inserts surveillance records in a transaction. No Express process, `BACKEND_URL`, API proxy or service-role key is required.

## 1. Configure the frontend

At the repository root, create `.env.local`:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Use `VITE_` names for this Vite app. The `NEXT_PUBLIC_` names shown by Next.js examples are not used. Keep `.env.local` out of Git; the existing ignore rule covers it. Only the publishable key belongs here. Restart Vite after changing configuration.

## 2. Apply the database migrations

In the Supabase SQL Editor:

1. Run `migrations/202610250001_surveillance_imports.sql` once for the initial tables. If you already ran it, skip it.
2. Run `migrations/202610250002_direct_supabase.sql` for the direct connection and complete eight-role definitions.
3. Run `migrations/202610250003_analytics_editing_audit.sql` for live analytics, individual record editing and persistent audit events. Existing installations with 001 and 002 already applied need only this third migration. Migrations 002 and 003 can be rerun and preserve existing imports.

Migration 002 adds a protected `roles` table, a `profiles.role_id` relationship, shared-unit reading, database validation, and these APIs:

- `list_surveillance_imports()` — permitted history and previews.
- `save_surveillance_workbook(p_id, p_workbook, p_error)` — permission checks, canonical validation and atomic saving.
- `delete_surveillance_import(p_id)` — I.T. Personnel only, with cascading record deletion.
- `update_my_profile(p_full_name)` — update your own name without changing role or unit.

The old `save_surveillance_import` function is disabled for clients because it accepted client-generated status and records. The new function recomputes both in PostgreSQL.

The project’s publishable key cannot run schema migrations. Apply these files through SQL Editor or your authenticated Supabase migration tooling; do not put an administrator key into the React app.

## 3. Create authentication users and assign profiles

Empty Authentication and profile lists are expected after running the migrations: the migrations create the schema and permissions, not login accounts. Supabase manages login accounts in `auth.users`; application information belongs in `public.profiles`. There is no separate `public.users` table to populate.

Create the login accounts first:

1. Open your project in the Supabase dashboard and choose **Authentication → Users**.
2. Choose **Add user → Create new user**.
3. Enter one of the test email addresses below and its agreed test password (`test123` for these development accounts).
4. Enable **Auto Confirm User** when offered so the test account can sign in without accessing the test email inbox.
5. Repeat for all eight accounts. Their UUIDs are generated by Supabase; do not invent UUIDs or store passwords in the profiles table.

```text
admin_clerk_test@email.com
medtech_test@email.com
radtech_test@email.com
physical_therapist_test@email.com
nurse_test@email.com
medical_officer_test@email.com
hseu_analyst_test@email.com
it_personnel_test@email.com
```

The `setup-test-profiles.sql` script is configured to assign all eight test accounts to **Victoriano Luna Medical Center**, as agreed. Once the eight Authentication accounts exist, run that script in SQL Editor. It checks for missing accounts and unfilled placeholders before writing profiles and never stores passwords. You can edit the provided test full names as well.

Copy the current file into a new SQL Editor query and run the entire `do $profiles$ ... $profiles$;` block. Clear any text selection first so the editor runs the whole block. This version uses no temporary tables and can be rerun safely. If you previously received `relation "profile_assignments" does not exist`, replace the older query text with this current version.

All eight assignments use the identical value `Victoriano Luna Medical Center` so the staff accounts share access to that unit's imports. Roles do not determine hospital assignments.

After the script succeeds, **Table Editor → profiles** should contain eight rows, linked to the UUIDs shown under Authentication. The `roles` table should also contain eight role definitions from migration 002. Restart the app and sign in with the I.T. Personnel account to verify the connection. Creating a login alone does not grant access until its profile has a role and assigned unit.

The script creates or updates each user's profile using the real UUID from `auth.users`. It assigns the exact role IDs supplied for this system:

```text
admin-clerk, medtech, radtech, physical-therapist, nurse,
medical-officer, hseu-analyst, it-personnel
```

If profiles already exist, migration 002 maps recognized role labels to their IDs. Review every account's assigned unit and role. Missing or unknown profiles fail closed; the application never defaults to I.T. Personnel.

## 4. Start the application

```powershell
npm.cmd install
npm.cmd run dev
```

Open the URL printed by Vite and sign in with an account from Supabase Auth. There is no separate backend command; the unused Express project and old nested scaffold have been removed.

## Access rules

The protected role definitions reproduce the eight-role matrix from `src/data/dictionary.ts`. The application hides unauthorized modules and gates their features; database policies and functions enforce import operations separately.

- Medical Technologist, Radiologic Technologist, Physical Therapist and Nurse can upload and read imports from their assigned unit.
- Medical Officer can read their assigned unit's imports and cannot upload or delete.
- HSEU Analyst can review incomplete/error summaries from their assigned unit. This import-errors view returns metadata and validation details without patient rows. The underlying workbook/record tables are inaccessible to this role through the import APIs.
- Admin / Information Clerk has no upload/import-history privileges. Data Management provides a demographics-only individual-record view and editor; clinical fields are omitted at the database boundary.
- I.T. Personnel can read imports across units, upload, and delete imports.
- Users can update their own full name. Roles, upload privileges and assigned units are administrator-managed; users cannot change them through profile editing or auth user metadata.

Surveillance tab and export permissions follow the role matrix. Medical Officers also have read-only access to their assigned unit's persistent Logs. I.T. can view events across units. Other roles can view their own recent activity, but cannot read the system-wide audit log.

## Live analytics and exports

The dashboard and Analysis & Export page call `get_surveillance_analytics`. Aggregation occurs in PostgreSQL across every matching record, so Supabase's default row-return limit does not truncate counts. Filters include reporting dates, disease, province, and (for I.T.) assigned unit. Staff and analysts are scoped to their assigned unit. I.T. can aggregate across units.

Counts represent uploaded rows, not unique patients. Incomplete records participate in totals. Files with incorrect columns have no surveillance records and do not contribute. Missing or invalid `RP DATE` values contribute to all-time totals, but not dated charts or date-range filters. Weekly comparisons use the week containing the latest reporting date in the filtered data and its preceding week; no percentage is invented when the preceding week has zero records.

`export_surveillance_analytics` requires full surveillance access. It generates aggregate groups using reporting week, disease, province, assigned unit, reporting unit, classification, sex and five-year age band. Names, case IDs, ranks, service identifiers and raw patient rows are not returned. Both real CSV and XLSX downloads are supported. The export request is recorded in the database before the data is returned. Charts and histories have Refresh controls; navigating to a module fetches current data. Realtime replication/subscriptions are not required.

## Individual record editing

Data Management's Individual records section calls `list_surveillance_records`, using server-side pagination and searching only permitted fields. Analysts cannot retrieve patient rows through this API. Clerk views exclude all clinical fields. The editor enables only fields the role may edit:

- Demographics: `CASE ID`, `RANK`, `OS`, `SURNAME`, `FIRST NAME`, `MIDDLE NAME`, `SEX`, `AGE`, `PROVINCE`.
- Clinical/reporting: `RP DATE`, `RP UNIT`, `DISEASE`, `CASE CL`, `DS DATE`.

These are permission groups for the finalized surveillance schema. It has no physical-exam-specific fields, so the integration does not invent a physical-exam editor. The mapping is enforced by `record_field_permissions`, independently of the browser.

`update_surveillance_record` checks the user's current role, assigned unit, allowed fields and expected record version. It validates edited dates and ages, updates the original worksheet cell positions and canonical record, recomputes completeness, and writes an audit event in one transaction. Another user's intervening edit causes a clear conflict message; refresh and reopen the record instead of overwriting it. Blank cells remain missing, but an entire record cannot be cleared through editing. No edit fields allow moving records to another import, sheet or assigned unit.

## Persistent audit events

`audit_events` is an append-only ledger for application roles, containing server timestamps and trusted actor/role/unit snapshots. Database triggers record import creation/deletion, record edits and profile changes. Read/export functions record their own operations. Record-edit details include changed field names and source row information; they do not copy old/new patient values into the log. Deleting an import preserves its audit events.

The app records successful interactive logins, logouts and inactivity sign-outs through `record_access_event`. Authentication failures remain in Supabase Auth's system logs; they are not attributed to a user by an unauthenticated browser. No synthetic events or generated IP addresses are used. Profile and Home activity show the current user's recent events. The Logs page supports persistent filtering and pagination. Database permissions prevent application clients, including I.T. accounts, from updating or deleting ledger entries; trusted database administrators retain maintenance access. Audit-history retention is not automatically scheduled by this migration.

No previous in-memory demo history is backfilled. Events begin when migration 003 is applied. Existing surveillance rows receive initial version 1 for editing. The original imported XLSX bytes are still not stored.

## Workbook storage and validation

The original fourteen headers and their order are required. Case and repeated/surrounding whitespace are normalized. Reference sheets are excluded from records. Interior empty rows are incomplete; unused trailing template rows are ignored. A header-only template is incomplete.

Supabase stores the parsed workbook and validation in `surveillance_imports`. Valid-column workbooks produce records in `surveillance_records.record_data`, with the fourteen column names as JSON keys. Blank values become `null`; the red word “missing” is a display label. Column errors are retained in history and create no surveillance records. Original XLSX file bytes are not stored.

Limits are 5 MB per source file, 200 worksheets, 100,000 parsed rows, 100 columns per worksheet, and 20 MB of parsed JSON. Database validation checks shape and completeness. Date ranges, disease vocabulary, logical duplicates, and the source hospital's correspondence to the uploader's assigned unit are not enforced yet.

Browser-local imports from the earlier prototype are not automatically uploaded or shared. Re-upload the original workbook after signing in to save it in Supabase. A database save failure is displayed explicitly and does not create a fake successful history entry.

## Verification

```powershell
npm.cmd run build
npm.cmd run lint
npm.cmd test
npm.cmd run check:connection
```

`npm test` checks the finalized Excel format and real browser parser, then runs the migrations against local PostgreSQL through PGlite, including RLS, role escalation attempts, atomic import saving, analyst redaction, assigned-unit sharing, profile provisioning and deletion rules. It does not change your hosted project. `check:excel` and `check:supabase` run those groups individually. `check:connection` makes a read-only request to the configured project without printing credentials or patient data.

After applying the hosted migration, verify a real sign-in/upload in the browser and confirm the rows in Table Editor. The local database/browser tests do not substitute for checking your hosted account provisioning.
